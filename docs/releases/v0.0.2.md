# v0.0.2 "In time"

Released **2026-11-06**. Fixes found by testing v0.0.1 through a real audio
output, and time-driven drawing (progress and lyrics) made exact and cheap.
Still the core and `jf`; the native apps start in Milestone 2.

## Fixed

* **The end of the last track was cut by 12–20 ms.** When the queue ended,
  the engine stopped once its own buffer was empty, while the output still
  held audio. It now waits for the output's reported delay plus one period.
  Measured: 0 ms lost.
* **Progress and lyrics ran ahead at every start, then jumped back.** The
  playback clock started at the first write, but an output can take a while
  to begin (0.5–1.3 s with ALSA through PulseAudio here; PipeWire behaves
  alike). The clock now starts when the output consumes its first samples,
  and the output's own delay is accounted for from then on.
* **A harmless output report stopped playback.** cpal reports underruns and
  an unsupported pause through the same channel as a lost device; any of them
  failed the stream. Only a missing device or audio server, or an invalidated
  stream, is fatal now.
* **`jf` hung after a real output failure.** Playback now stops with the
  error, and the next Play opens the output afresh (a replugged device, a
  restarted audio server).

## Animation

* **Lyrics on time.** Measured against the sound, through the real output
  path (virtual speaker, raw recording on the same clock):

  | Lyric line shown minus heard | v0.0.1 | v0.0.2 |
  | --- | --- | --- |
  | First line after start | −6 ms in one run, −933 ms in another | −4 to −10 ms |
  | Later lines | +36 to +84 ms | −4 to −10 ms |

* **`DisplayClock`** (`jf-core::timing`): the position to draw, smoothed and
  monotonic. Re-anchoring corrections are slewed, never jumped, so a progress
  bar or word sweep does not jitter; seeks, pauses and new tracks show at once.
* **`LyricTimeline::next_change`**: the next time the line or word changes or
  a word finishes, so views redraw only when something visible changes. A
  property test checks it against a millisecond scan.
* **Contract vectors** in `tests/contract/lyrics-cursor.json`: cursor and
  `next_change` results for four fixtures, for every shell to replay.
* **`jf play` live view:** the current lyric line with a sweep that lights
  each sung character in the artwork's accent colour, its translation, and a
  half-cell progress bar; sung lines scroll up. About 5 redraws a second for
  progress and 11 with the sweep (60 for a per-frame redraw), and nothing
  while paused. CPU: 1.5 % of one core with or without the view, for decode,
  output and drawing together (virtual speaker, 44.1 → 48 kHz).

## Testing

* `tools/cloud-audio-check/run.sh` (also the CI `audio` job) now checks lyric
  sync to ±30 ms besides gapless joins, dropouts, pitch, and audio lost at the
  start and end. Its v0.0.2 result: joins clean for FLAC, MP3 and Vorbis; 0 ms
  lost at the end; lyrics −7 to −10 ms (about the recording method's own
  precision).
* 259 tests pass and one benchmark is ignored by default; `fmt`, `clippy`,
  `xtask tokens --check` and `cargo deny` pass.

## Known limitations

* Not yet run on real audio hardware, macOS or Windows; sync relies on the
  delay each audio system reports, measured here on PulseAudio's virtual
  speaker only.
* Through PulseAudio's or PipeWire's ALSA plugin the output cannot pause, so
  the stream keeps running (playing silence) while paused or idle. That costs
  wakeups against the Still-mode CPU budget and belongs with output-device
  handling (spike S3).
* `jf` reads the terminal width from `COLUMNS` (80 when unset); a narrower
  terminal wraps long lines and breaks the live view.
* Everything listed for v0.0.1 that is not fixed above still applies.
